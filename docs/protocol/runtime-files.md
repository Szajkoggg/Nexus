# Server-owned runtime files

Part of [the protocol](../PROTOCOL.md).

## Server-owned runtime files

Written only by the server's queue engine; agents never touch them.

| File | What |
|---|---|

One writer: the server. See ["Pushing what was accepted"](git.md#pushing-what-was-accepted) |
| `queues/<id>/plan.yaml` | The queue's place in the plan (see ["The plan"](planning.md#the-plan)): `by`, `reason?`, `after` (the queues it waits for, each with `queue`, `by`, `at`, `reason?`), `created_at`, `updated_at`, `started_at?`, `proposal?`, `decisions`. One writer: the server; it stays after the queue starts (marked `started_at`), and taking the queue out of the plan removes it |
| `queues/<id>/start.yaml` | The queue's next start as planned (see ["The plan"](planning.md#the-plan) and ["Schedules"](planning.md#schedules)): `at?` (a schedule: the time, ISO 8601; with `usage`, `claude` or `codex`, when that is the usage window's reset plus the margin; without `at`, the options of a start by the plan; `after` only in files from before the plan, moved into `plan.yaml` at the server's start), the start's `runtime?`, `model?`, `effort?`, `session?` (a session to continue), `by` (`user` or `orchestrator`), `reason?`, `revision` (the queue's when planned), `created_at`, `failed?` (`at`, `reason`, `missed?`: it came due and the queue could not start; `missed`: a schedule more than 15 minutes late, the server not running at its time), `held?` (`since`, `kind`: `approval`, `checkout` or `limit`, `reason`: it came due but waits for the approval of the queue's current revision, for its checkout or for a place under the limit, and starts by itself; see ["The plan"](planning.md#the-plan) and ["One queue per checkout, and a limit"](git.md#one-queue-per-checkout-and-a-limit)). One writer: the server; a start of the queue or a cancel removes it |
| `queues/<id>/run.yaml` | The engine's intent for a queue: `session`, `after` (started by the plan: the queues that were done, a list; one id in older records), `state` (`running`, `pausing`, `paused`, `halted`, `finished`, `usage_wait`, `retry_wait`: a turn failed for a passing reason and is tried again at `resume_at`, `approval_wait`: a step ended while a newer revision waits for the user's approval, and the run goes on by itself once approved, see ["A new revision of a running queue never stops the running step"](queues.md#queueyaml); cleared by a turn that ends well or a new step), `failure` (the runtime's code for the failure being retried or that halted the run, e.g. `overloaded`), `pause` (the kind of a stop by the user or an orchestrator that paused the run: `pause` (Pause), `stop` (Stop, Stop now), `reject` (a rejected step); kept while the run reaches `paused`, removed when it goes on or is held for an update; the orchestrator is told of a requested pause reached by `pause: pause`, never by the reason's text; a file from before it has none, and then a reason starting "paused by the user" counts as a pause), `resume_after_restart`, `held` (a `running` run held at the limit on queues running at once: `since`, `kind` `limit`, `reason`, also the run's `reason` while held; a missing model or effort is the runtime's default), `from_defaults` (which of the three came from the project's defaults: resolved again when each step opens; see ["Runtime, model and effort per step"](runtimes.md#runtime-model-and-effort-per-step)), `started_at`, `ended_at` (when it last stopped going: set when it becomes `finished`, `halted` or `paused`, kept while it stays so, removed when it goes on; older files without it fall back to `updated_at`), `summary_asked` (context care: the step whose context summary Nexus asked for; asked once), `carry` (inbox entry ids a turn the runtime started by itself at a step's end had taken in before Nexus ended it to switch sessions: they go to the fresh session's first turn, and the switch removes them; kept here so a server that ends before the switch does not lose them, queue LH), `switches` (each fresh session, oldest first: `at`, `from` and `to` session, `step` the new session began with, `why`: `context` (context care; a record without `why` is this), `runtime` (the step runs on another runtime), `refactor` (the closing refactoring step, see ["The closing refactoring step"](queues.md#the-closing-refactoring-step)) `usage` (in the middle of a step, on its fallback: see ["Fallback when usage runs out"](runtimes.md#fallback-when-usage-runs-out)) or `idle` (context care after an idle hour, with `idle_minutes`; see ["Context care"](runtimes.md#context-care)), `fill` of the old one from 0 to 1 and `tokens`, its context tokens, when known (`tokens` since queue CT), `summary`: `written` by the worker, `asked` and then written, or `fallback`), `revision` (the queue's revision the run goes by: written at the start, moved to the current approved one at the end of a step), `checks` (the project's `defaults.checks` as they were at the start, when there were any: every step of the run runs them before the queue's own; see "The project's checks"), `fallbacks` (each step that opened on its fallback, and each that opened on its own values again after one did, oldest first: `at`, `step`, `runtime`, `model`, `effort` it opened on, `from` (its own values), `reason`, `back: true` for a switch back; see ["Fallback when usage runs out"](runtimes.md#fallback-when-usage-runs-out)). Start refuses a `stopped` queue, naming the step and the stop's reason, and writes `revision`; it also refuses while the run holds its session (`approval_wait` included). Resume refuses a stopped or cancelled queue, an unapproved revision unless the run is of an older one (`revision` below the queue's; a run record without `revision` is older when a revision was replaced, in `history`, after its `started_at`: such a run goes on mid-step while the newer revision waits), and an `approval_wait` run until its revision is approved. A run of an older revision is resumed like any: a revision changes no started step. Archived records are `run.<time>.yaml` (see ["Changes and lifting a stop"](queues.md#queueyaml)) |
| `sessions/<id>/runtime.json` | A launched session's live facts: process state (`starting` until its process is up, `working` from a turn's start to its end, `idle` between turns, `exited`: a worker's process exits when its run finishes, when its session is switched for a fresh one, when its queue starts afresh in another session, and when its queue is done or cancelled, before the queue's worktree is cleaned up; a paused or halted run's process stays for its Resume, which goes on in it, see DESIGN.md, ["When a worker's process ends"](../design/engine.md#when-a-workers-process-ends)) and pid, model, context tokens and window, turns, cost; `interrupted` (`at`, `asked`, `handoff?`): a chat turn an update's hand-over cut off, until the next server goes on with it (see ["The chats during an update"](api.md#server-api)); `conversation_saved?` (Claude Code sessions): false from a fresh start until the process shows it read a message (Claude Code saves the conversation then), true after; the next process resumes the session (`--resume`) unless it is false, else starts afresh with the same id (`--session-id`); a record without it (written before queue RN) counts as saved (DESIGN.md, ["When Claude Code saves a conversation"](../design/engine-failures.md#failures)); `last_turn?` (`started_at`, `ended_at`): the session's latest turn that ended, which context care's idle switch reads (["Context care"](runtimes.md#context-care); absent before the first turn ended and in records written before queue FI); `turn_open?` (`started_at`, `queue?`, `step?`, `fallback?`): the turn under way, from its start until its record is written to `turns.jsonl` (queue CK): a server that crashed leaves it, and the next server records that turn as `interrupted` and drops it |

A session launched by Nexus has `launched_by: nexus`, its `runtime` (claude or codex), a `native_id` (a Claude session's UUID, chosen
by Nexus; a Codex thread's id) and the `model` and `effort` it was started with. A queue may also say `worktree: auto`: Nexus then creates the worktree
and branch when it starts the queue and writes their paths back into `queue.yaml`.

**The project's checks.** A project's `defaults.checks` (project only, a list of commands; empty by default; in Nexus
`npm run lint`) are checks every step of every queue of the project runs, before the queue's own `checks`. A run fixes
them when it starts (`checks` in `run.yaml`): a change of the setting reaches a queue at its next start, not its next
step, and a resume goes on with what its run fixed; a run from before the setting has none. The step's opening lists
them first under "Checks for every step", then the queue's own; a check both name (compared trimmed) is listed and
run once. The orchestrator's review notice counts a missing one like a missing check of the queue. The settings API
stores them trimmed, without empty or repeated entries. The approval view and the queue's details show them before
the queue's own, marked "(project)": the run's while it has one that has not finished, else the setting now.

**Worktree setup.** A project's `defaults.worktree_setup` (project only; none by default; in Nexus `npm ci`) is a
command run once in each new worktree Nexus makes for a queue (`worktree: auto`), so the worktree can build and test
(its own `node_modules`, for example). When Nexus makes the worktree it records `setup` in the queue's `git.yaml`; the
engine runs the command through the shell in the worktree before the run's first step opens (no step opens while it
runs, at most 30 minutes) and records `done_at`. A failure (an exit code other than 0, or the time limit) is tried
once more; failing again, it halts the run with the reason, `the worktree setup command (<command>) failed twice: exit
code <n>; its output ends: <output>` (queue CK), and records it under `failed`; when the run goes on (Continue, resume), the project's command as it is then runs again in the same
worktree. A run paused or stopped while the first try ran (the user's Pause or Stop, an update's drain, the server's
end) gets no second try: nothing is recorded under `failed`, the run does not halt, and the command runs again when the
run goes on (queue LCK, survey LC3 F4). A run paused or stopped while the second try ran is left the same way: its
failure is not recorded under `failed`, the run does not halt, and the command runs again when the run goes on (queue
LCG, survey LC4 finding 6). A worktree the queue names by path, an existing one, and the project's own checkout get no setup. A success
records the commit it ran on (`sha`); a change of its inputs (`defaults.worktree_setup_inputs`) since then runs it again
before a check set or after a merge of the base at a step boundary (queue MI): ["The integration step"](git.md#the-integration-step), "Without a
model".

**Merging back by itself and resolving conflicts** (`defaults.merge_back`, `defaults.resolve_conflicts`; global, with a
project override; both off by default, so a new project merges back only by the user's hand until the user turns
them on): with `merge_back`, Nexus merges a queue with a worktree of its own back by itself, when all its steps are
accepted, the merge has no conflict and its integration step's checks pass; with `resolve_conflicts`, the integration
step's worker tries to resolve a conflict with the current base, judged by the checks and the step's review, and only
one it cannot resolve waits for the user (see ["The integration step"](git.md#the-integration-step)). How the base then moves: "Merge back and clean
up".

The event `review.accepted` (`queue`, `step`, `text?`, `to?`), written by the user or an orchestrator, accepts a step
held in `review`.

**Accept with a note** (the user's). The note is optional; empty means a plain accept. `to` says where it went:
- `next` (the default): the next pending step of the queue gets it as a note from the user (`notes/`), delivered when
  that step starts, like any note on a pending step.
- `orchestrator`: the note stays on the event, and the orchestrator is told it once per project, like a chat message
  of the user: it starts an orchestrator that has no session and is told whatever `notify` says (but not while an
  update drains; then after the restart). The key `notify:note:<event id>` in any orchestrator session's
  `applied.jsonl` marks it told, so a reset orchestrator is not told again. The chat shows the note.
- On the queue's last step (no pending step after it) the note always goes to the orchestrator.
An acceptance with a note pushes like any other (see ["Pushing what was accepted"](git.md#pushing-what-was-accepted)).

**Reject** (the user's only, `POST …/steps/:s/reject` with an optional `text`; only on a step waiting for the user's
review). The server writes `review.rejected` as the user's session and pauses the run (`run.yaml`: `state: paused`,
the reason, `pause: reject`, `rejected: <step>`). Nothing is reverted.
- The step's status is `rejected` (its `reason` is the text). It is never run again.
- The derived queue has `rejection` (`step`, `at`, `text?`, `revision`: the revision current when it came) and is
  `paused`, with the reason, until the user approves a newer revision. Then the rejection lifts.
- Once the rejection lifts, the rejected step counts as closed, like a skipped one (`stepClosed`): it keeps its
  status `rejected` and its reason, start and resume run what is pending, and the queue is `done` when every other step
  is finished (the run ends `finished`).
- The orchestrator is told once per project, like a note on an acceptance: whatever `notify` says, starting it if it
  has no session (key `notify:reject:<event id>`). It proposes what follows as queue revisions for the user's
  approval: a revert as a step, changes to the remaining steps, or a new queue (then the user can stop this one).
- While the rejection holds, start and resume are refused, and nothing of the queue is pushed (no push of an
  acceptance, no Push again). After the approval, resume goes on at the first pending step: a run paused by a
  rejection may resume although it is of an older revision (it takes the new one).
- The orchestrator's approval notice for such a queue says to resume it.
